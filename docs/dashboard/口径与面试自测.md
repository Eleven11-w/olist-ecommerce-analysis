# BI 看板口径与面试自测

## 数据口径

| 项目 | 定义 |
|---|---|
| 有效订单 | `order_status` 不属于 `canceled`、`unavailable`，且存在商品明细 |
| GMV | `SUM(price + freight_value)`；使用仓库统一的 items 口径 |
| 订单数 | `COUNTD(order_id)`，不能使用事实表行数 |
| 买家数 | `COUNTD(buyer_key)`；`buyer_key` 是原客户标识的 SHA-256 |
| AOV | GMV ÷ 去重有效订单数 |
| 事实表粒度 | 订单×英文品类；同一订单跨品类时会有多行 |
| 品类评分 | 每订单先取 `MAX(review_score)`，再按订单×品类计算平均值 |
| Cohort 留存 | 首购月为 cohort；第 n 月有任意有效订单即留存；第 0 月为 100% |

## 第 1 天必须掌握

1. **数据粒度**：为什么 99,002 行只对应 98,199 个订单。
2. **一对多 JOIN 风险**：订单、商品明细、支付、评价直接互连为什么会重复放大金额。
3. **可加指标与不可加指标**：GMV 可跨事实表行求和；订单数和买家数必须去重。
4. **口径统一**：BI 层只展示分析层已经冻结的定义，不在图表里修改分母或剔除规则。
5. **自动 QC**：固定基线如何捕获重复 JOIN、漏数、字段类型和筛选错误。
6. **发布数据最小化**：公开看板为什么不应携带数据库密码或不必要的原始标识。

## 常见面试追问

### 为什么事实表设计成订单×品类，而不是商品明细行？

订单×品类既保留品类筛选能力，又避免同一订单同一品类多件商品造成订单和评分重复。商品金额先聚合到该粒度，GMV仍可安全求和。

### 为什么订单数不能用 COUNT？

多品类订单在事实表中有多行，`COUNT` 会把它重复计算；应使用 `COUNTD(order_id)`。

### 为什么没有把支付表 JOIN 进来？

订单商品和支付记录都可能是一对多，直接关联会形成乘积并放大 GMV。分析层已用支付金额做独立交叉核对，BI 层只使用 items 主口径。

### 为什么评价先按订单取 MAX？

分析层发现评价表存在重复 `review_id`，已冻结为每订单取一条评分的口径。BI 层继承该规则，使各展示版本结果一致。`MAX` 是去重规则，不代表选择“最好评价”进行业务解释。

### 为什么要同时支持 MySQL 与 CSV？

MySQL 是正式 SQL 复现路径；CSV 路径用于本机没有数据库会话凭据时，从仓库内冻结的原始数据生成同一事实表。两条路径都必须通过同一组 QC，且 README 要记录实际使用的路径。

### QC 全通过是否说明分析结论正确？

不能。QC 只证明数据结构和冻结指标没有漂移；业务解释仍需检查时间窗、样本限制和描述性结论边界。
